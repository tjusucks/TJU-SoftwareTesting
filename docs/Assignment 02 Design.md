# Assignment 02 项目设计简报

## 1. 目的

本报告用于统一本次 Assignment 02 的项目设计思路，重点说明：

- AutoTestDesign 工具的推荐设计方式
- 主要交付物及其来源
- 哪些内容适合由 AI 工具生成，哪些内容需要人工完成
- 5 人小组的简单分工方式

## 2. 项目设计参考

### 2.1 总体思路

本次项目不建议继续使用“一个 skill 完成全部工作”的方式。

更合适的做法是：

- 使用 **1 个总控 skill** 负责流程编排
- 使用 **多个子 skill** 分别负责不同工作
- 输出统一的中间结果，最后汇总为交付物

这样更符合 Assignment 02 对“AI-driven AutoTestDesign tool”的要求，也更方便展示工具的可维护性和交互性。

### 2.2 推荐 skill 划分

建议采用下面的简单划分：

1. **Orchestrator / Planner**
   - 负责整体流程
   - 决定调用哪个子 skill
   - 汇总最终结果
   - 承接人工 review / revision
   - 体现“designer participation”

2. **Requirement Structuring**
   - 读取需求文本 / CSV / 用户输入
   - 提取 requirement items、约束、条件、预期行为
   - 输出结构化需求结果

3. **Risk Analysis**
   - 对需求或模块进行风险打分
   - 给出 High / Medium / Low 优先级
   - 输出风险分析结果，供测试计划使用

4. **Black-box Design**
   - 生成等价类、边界值、决策表等黑盒测试设计
   - 输出测试用例、coverage items 和 traceability

5. **White-box Modeling**
   - 对重点模块生成状态迁移或逻辑路径
   - 作为加分项支持白盒测试设计

6. **Test Generation（可选）**
   - 将部分测试设计转换为可执行测试代码
   - 用于支撑执行验证
   - 这是可选增强项，不是本项目最低必需部分

说明：

- 不再单独拆分 **Review / Revision** skill，相关能力直接体现在 **Orchestrator** 中。
- 不再单独拆分 **Exporter / Report Support** skill，导出和报告支持可以直接包含在各个 skill 的输出中。
- **测试计划（Test Plan）是必须交付物**，必须由人工主导完成。
- **可执行测试代码是可选项**，用于支撑“Test Tool Implementation”，不是 black-box / white-box 的唯一核心输出。

### 2.3 推荐 target app

建议继续沿用 **RealWorld 这类已有 requirement specification 的 web app**。

原因：

- 有现成需求规格，便于工具解析
- 功能模块较多，适合做风险分析和测试计划
- Web app 容易做黑盒测试与自动化测试
- 演示效果更直观

建议做法：

- **风险分析报告和测试计划**：面向整个 target app
- **详细测试设计与执行文档**：只选一个重点模块展开

可选重点模块：

- Authentication
- Article lifecycle
- Comment / Favorite / Follow

## 3. 主要交付物说明

| 交付物                    | 内容                                                         | 说明                                       |
| ------------------------- | ------------------------------------------------------------ | ------------------------------------------ |
| 1. AutoTestDesign 工具    | 源代码、prompt、README、演示视频                             | 这是工具本体，不只是一个 skill 文件        |
| 2. 风险分析报告           | 针对 target app 的风险分析                                   | 不是分析工具本身                           |
| 3. 测试计划               | 范围、测试项、测试策略、进度、分工、框架、成本估算           | 权重最高，必须写清楚                       |
| 4. 详细测试设计与执行文档 | 针对一个重点模块的详细测试设计、结果分析，以及可选的脚本实现 | 需要结合黑盒和白盒技术，测试代码不是必须项 |
| 5. 最终 PPT               | 项目展示材料                                                 | 用于课堂展示                               |
| 6. 演示视频               | 展示工具如何使用                                             | 属于工具交付的一部分                       |

## 4. AI 生成 vs 人工完成

建议把本项目理解为：

- **AI 工具负责生成测试资产**
- **人工负责审查、决策、整合和正式成文**

### 4.1 适合由 AI 工具生成的内容

| 内容             | 说明                                           |
| ---------------- | ---------------------------------------------- |
| 结构化需求结果   | requirement items、输入约束、条件、预期行为    |
| 风险分析候选结果 | risk score、priority、risk rationale 初稿      |
| 黑盒测试设计     | 等价类、边界值、决策表、测试用例初稿           |
| 白盒模型候选结果 | 状态迁移、路径序列、覆盖建议                   |
| traceability     | requirement 到 coverage item、test case 的映射 |
| 导出型工件       | JSON、CSV、测试用例表、traceability matrix     |
| 测试套件优化建议 | 优先级排序、smoke/regression/full suite 划分   |

### 4.2 需要人工完成或最终确认的内容

| 内容             | 说明                                                   |
| ---------------- | ------------------------------------------------------ |
| target app 选择  | 这是项目决策，不能完全交给 AI                          |
| README 最终版本  | 需要与实际项目保持一致                                 |
| 风险分析报告     | AI 可生成初稿，但正式报告需人工组织和确认              |
| 测试计划         | 项目范围、组织结构、框架选择、成本估算需要人工主导     |
| 详细测试设计文档 | AI 提供测试资产，人工负责整合、解释和结果分析          |
| 测试脚本实现     | 属于可选增强项，可以借助 AI 生成，但需要人工调试和运行 |
| PPT 与演示视频   | 必须由人工完成                                         |

### 4.3 简单结论

- **AI 负责“生成”**
- **人负责“决定、修改、整合、提交”**

## 5. 5 人分工指南

分工目标：

- 简单清楚
- 每个人有一个主要责任
- 避免多人重复负责同一件事

### 5.1 推荐分工

| 成员   | 主要负责           | 需要负责的具体工作                                                                                             | 主要交付                                               |
| ------ | ------------------ | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 成员 1 | 总控与整合         | 开发 orchestrator、整合各 skill 输出、统一数据格式、运行最终全流程、汇总交付物                                 | README、最终汇总版工具结果、PPT 主线                   |
| 成员 2 | 需求解析           | 开发 requirement structuring skill、整理 requirement input、优化该 skill prompt、运行 skill 生成结构化需求结果 | requirement input、requirement IDs、结构化需求结果     |
| 成员 3 | 风险分析与测试计划 | 开发 risk analysis skill、优化该 skill prompt、运行 skill 生成风险结果、主写测试计划                           | 风险分析结果、风险分析报告、测试计划                   |
| 成员 4 | 黑盒测试设计       | 开发 black-box design skill、优化该 skill prompt、运行 skill 生成黑盒测试资产、整理 traceability               | coverage items、黑盒测试用例、详细设计文档中的黑盒部分 |
| 成员 5 | 白盒与执行验证     | 开发 white-box / test generation（可选）相关能力、选择测试框架、运行测试、整理结果                             | 白盒设计结果、可选测试脚本、执行结果、演示视频         |

### 5.2 每个人具体要做什么

#### 成员 1：总控与整合

主要负责把项目真正拼成一个可提交的整体。

具体工作：

- 负责工具总体结构设计
- 开发和维护 orchestrator
- 统一 requirement ID、risk ID、test case ID 命名
- 运行最终完整流程，检查各模块输出是否能接上
- 汇总所有交付物内容
- 主写 README
- 负责最终 PPT 主线与整体检查

#### 成员 2：需求解析

主要负责“工具如何读懂需求”。

具体工作：

- 整理 target app 的 requirement source
- 开发 requirement structuring skill
- 优化 requirement structuring prompt
- 运行 skill，生成结构化需求结果
- 维护 requirement IDs
- 配合成员 1 保证结构化输出格式稳定

#### 成员 3：风险分析与测试计划

主要负责“风险判断”和“计划文档”。

具体工作：

- 开发 risk analysis skill
- 优化 risk analysis prompt
- 运行 skill，生成 risk score 和 priority
- 主写风险分析报告
- 主写测试计划
- 完成高层测试策略、进度安排、成本估算

#### 成员 4：黑盒测试设计

主要负责最核心的 black-box testing 输出。

具体工作：

- 开发 black-box design skill
- 优化 black-box design prompt
- 运行 skill，生成等价类、边界值、决策表结果
- 生成测试用例和 traceability
- 主写详细测试设计文档中的黑盒部分
- 和成员 5 对接，提供后续可执行测试输入

#### 成员 5：白盒与执行验证

主要负责白盒部分和执行验证部分。

具体工作：

- 设计重点模块的白盒分析方式
- 开发 white-box modeling 能力
- 如有需要，补充 test generation（可选）能力
- 选择测试框架
- 运行测试或部分测试脚本
- 汇总执行结果和结果分析
- 录制演示视频

### 5.3 简单协作规则

为避免混乱，建议遵守下面 5 条：

1. **先统一 target app 和重点模块**
   - 不要每个人按自己的理解写

2. **每个 skill 只设一个开发负责人**
   - requirement、risk、black-box、white-box/orchestrator 各有唯一负责人

3. **每个 skill 负责人也负责该 skill 的 prompt 优化和运行**
   - 不要把“开发 skill”和“运行 skill”拆给不同人

4. **每份正式文档只设一个主负责人**
   - 其他人提供内容，不要多人同时主写同一份文档

5. **先生成结构化结果，再写正式文档**
   - 先让工具产出，再整理成报告和 PPT

## 6. 推荐推进顺序

建议按下面顺序推进：

1. 选定 target app 和重点模块
2. 确定 skill 划分和总体结构
3. 跑通一轮需求解析 → 风险分析 → 黑盒设计
4. 补充白盒设计和交互式修改
5. 导出测试资产
6. 撰写风险分析报告
7. 撰写测试计划
8. 撰写详细测试设计与执行文档
9. 完成 README、视频、PPT

## 7. 总结

本项目建议采用“**多 skill 协作 + 人工审查整合**”的方式完成。

核心思路是：

- 使用 AI 工具自动化生成测试资产
- 由人工负责项目决策、文档组织、测试执行与展示
- 用简单明确的 5 人分工降低协作混乱

如果执行得当，这种方式既能满足 Assignment 02 的功能要求，也更容易在报告和展示中说明项目结构与团队协作逻辑。
